# 异常处理按钮路由整改设计

## 目标

异常页的每个处理按钮必须明确说明“点击后能解决什么”，并直达负责该问题的维护页面。禁止使用“查看识别结果”之类没有修复含义的兜底按钮，也禁止未知异常默认跳转到商品匹配页。

本次只在 `6173` 验证环境实施；不更新 `5173`，不重启现场后端、解析服务或采集器。

## 按钮映射

| 异常状态 | 按钮文案 | 目标页面 | 带入内容 |
| --- | --- | --- | --- |
| `product_unmatched` | 补商品规则 | 商品匹配 | 当前商品行、采集轮次和异常原因 |
| `sku_unmatched` | 维护 SKU | 商品/SKU | 已命中的商品 |
| `sku_ambiguous` | 指定 SKU 匹配 | 商品匹配 | 已命中的商品、当前商品行、采集轮次和异常原因 |
| `image_unmatched` | 补 SKU 图片 | 商品/SKU | 已命中的商品 |
| `conflict` | 检查冲突规则 | 商品匹配 | 当前商品行、采集轮次和异常原因 |
| `pending` | 检查解析结果 | 面单解析 | 当前采集轮次 |
| `unmatched` | 补商品规则 | 商品匹配 | 当前商品行、采集轮次和异常原因 |
| `special` | 不显示按钮 | 无 | 特殊单无需处理 |

## 交互约束

- 异常状态、按钮文案、建议文字和目标路由使用同一份显式映射，不能各写一套分支。
- 未识别的异常状态显示原始状态和“暂无处理入口”，不显示可点击按钮。
- 跳转到商品匹配页时只带入当前商品行作为规则样本，不加载整轮问题清单。
- 跳转到商品/SKU 页时自动选中已命中的商品；没有商品编号时不能错误打开任意商品。
- 不在异常页提供逐行人工确认、排除、审批或结果覆盖。
- 修复仍通过匹配规则或商品/SKU/图片资产生效，不能保存单行人工结果。

## 验证

- 为全部八种状态验证按钮文案、目标路径和查询参数。
- 验证未知状态不产生默认跳转按钮。
- 浏览器逐项点击 `6173` 的实际按钮，确认落点与当前商品行上下文。
- 前端类型检查、生产构建和针对性回归测试必须通过。
- 部署只替换 `6173` 前端，并保留上一阶段前端容器和 Git 标签。
