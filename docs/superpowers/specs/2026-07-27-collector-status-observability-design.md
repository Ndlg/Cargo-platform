# 采集器状态可见设计

## 目标

在现有“采集连接”页面直接看出采集器是否还有待补传记录、最后一次成功上传时间，
以及最近一次断线后重连的原因。状态采集不能中断打印采集，也不能改变采集水位和
任务归属。

## 已确认方案

复用现有采集器心跳和 `Collector.status_payload`，不新增数据库表、历史事件系统或
监控服务。

### 状态字段

- `queue_size`：本机打印数据库中，位于当前采集水位之后、尚未收到服务端确认的记录数；同一打印组件存在多轮未完成水位时，从最早水位计算且每条本地记录只计一次。
- `last_upload_at`：服务端确认一次上传后记录的 UTC 时间；上传失败不得更新。
- `last_reconnect_reason`：最近一次连接中断分类，只保存稳定类别，不保存异常堆栈或敏感内容。

重连原因限定为：

- `network`：网络连接中断或超时。
- `http`：服务端返回非鉴权 HTTP 错误。
- `auth`：采集器 token 无效或过期。
- `sqlite`：本机打印数据库暂时不可读。
- `state_save`：本地采集水位状态保存失败。

## 数据流

1. 采集器继续使用现有本地状态文件保存采集水位，并兼容旧状态文件。
2. 每轮心跳前，根据每个打印组件的数据库最大行号和最早未确认水位计算 `queue_size`。
3. 只有上传接口返回成功后才更新 `last_upload_at`；失败时水位和成功时间均不前移。
4. 现有异常捕获只记录对应的 `last_reconnect_reason`，随后继续后台重试。
5. 心跳把三个字段发送给现有接口。
6. 后端原样存入现有 `status_payload`。
7. 现有“采集连接”详情卡增加“最后成功上传”和“最近重连原因”，继续使用已有
   “队列积压”位置，不新增页面。

## 失败边界

- 状态统计失败时显示未知，不阻断采集、补传或本地状态保存。
- 未开始采集时积压为 0。
- 上传响应丢失时允许重传同一来源记录，服务端继续按来源记录号避免重复入库。
- 状态字段不参与面单识别、商品匹配、导出或采集任务时间窗判断。

## 不做

- 不保存掉线历史列表。
- 不新增告警、通知、日志检索或监控后台。
- 不增加数据库迁移和第三方依赖。
- 不部署或重启 5173 现场服务。

## 验收

- 上传失败后积压数大于 0，水位和 `last_upload_at` 不变。
- 重连补传成功后积压归零并更新 `last_upload_at`。
- 网络、HTTP、鉴权和 SQLite 异常能得到稳定的重连原因。
- 后端能保存并返回三个状态字段。
- 采集连接页面能显示三个状态字段，前端类型检查通过。
- 后端全量测试和 6173 数据副本覆盖守门通过。
